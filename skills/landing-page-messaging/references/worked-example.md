# Building a StoryBrand Worked Example

**Fictional teaching example.** All organizations, participants, numbers, and outcomes are invented for this exercise, not reported results or a case from the book.

## Visitor and problem

Visitor: an independent tutor who tracks lesson changes through messages. Desired action: request a product walkthrough. Working problem: difficulty seeing which changed times remain unconfirmed. This is a fictional positioning assumption requiring real customer research, not a quotation from a customer.

## Credibility and boundaries

The fictional prototype displays a pending list and permits manual status changes. Use a clearly labeled prototype screenshot. No customer testimonials or time-saving figures exist. Exclude “eliminates no-shows,” “trusted by hundreds,” and any claim of automated message sending.

## Steps and next action

Walkthrough flow: request a time; receive a scheduling reply; see the prototype in a short call. Primary button: Request a walkthrough. Destination: a request form asking for email and preferred time. Secondary link: View the example screen. No payment or immediate account creation is implied.

## Page draft

**Headline:** See which lesson changes still need a reply.

**Supporting line:** LessonLoop gives independent tutors one view of pending confirmations.

**Problem:** When lesson times change across separate message threads, checking who replied means opening them one at a time.

**Product:** Add a changed lesson and update its status when a reply arrives. The pending list keeps unresolved changes visible. The prototype currently requires manual updates.

**Proof:** Show a labeled prototype screen with invented names clearly marked as sample data.

**Next steps:** Request a time, receive a scheduling reply, and see the prototype in a walkthrough.

**Button:** Request a walkthrough.

## Review and measurement

“One view” and manual status updates match the fictional prototype specification. A reader might assume replies are captured automatically; the draft explicitly corrects that. Ask target readers what work remains manual and what the button does. If published later, measure qualified walkthrough requests per relevant visitor alongside misunderstandings. This is an unpublished draft; no conversion result is claimed.


## The decision record behind the draft

The following extends the same fictional scenario. Facts P1–P4 and observations R1–R3 are invented teaching inputs, not evidence about a real product.

| ID | Input | Consequence for the page |
| --- | --- | --- |
| P1 | Prototype supports adding a lesson change and manually changing its status | We can describe a maintained pending list |
| P2 | No messaging integration, reminder sending or calendar synchronization exists | Do not imply automatic capture or scheduling |
| P3 | Founder can conduct three 15-minute demonstrations this week | A request is subject to confirming a time; capacity is an internal planning fact |
| P4 | No paying users or measured time savings | Use sample-data demonstration, not testimonials or outcome statistics |

Initial internal copy was: “The smarter way to run your tutoring business. Get started.” This communicates neither the job nor the commitment. Three alternatives were considered:

- “Never miss a lesson again”: rejected because a confirmation tracker cannot guarantee attendance.
- “Automate your tutoring admin”: rejected because P2 contradicts automation.
- “See which lesson changes still need a reply”: selected because P1 supports a specific task.

The chosen audience is a tutor who already sends changes through messages and wants an additional list. Someone happy with their calendar alone is not automatically a good fit. The page should let that person recognize the mismatch.

## Mapping the message into an actual page

The customer wants to identify unresolved changes; the problem is checking separate threads. The helper offers a small tracking tool, with a demonstration as evidence. The plan distinguishes requesting a call from using the tool. The next action is a walkthrough request. The ordinary unresolved cost is repeated checking; the achievable improvement is a visible list of outstanding replies. These are original application choices, not customer quotations.

Version A uses the earlier page draft. Its headline is concrete, and its explanation mentions manual updates. But “one view of pending confirmations” still leaves open how replies enter that view, and the access steps appear below the main button.

## Fictional reader check

The facilitator shows the page without introducing the product and asks: “What would you use this for? What work would remain yours? What happens when you click?”

| Reader | Recorded interpretation | Diagnosis |
| --- | --- | --- |
| R1, tutor using messaging apps | “It pulls my replies into one place. The button creates my account.” | Wrong mechanism and access expectations |
| R2, tutor using a paper list | “I add the changes myself, then see what is still pending. I request a call.” | Intended meaning understood; buying interest still unknown |
| R3, tutor whose calendar already works | “Another place to update. I wouldn't use it.” | Relevance objection, not necessarily unclear copy |

R1's interpretation matters even though a later paragraph was technically accurate. The correction should reach the point where the false expectation forms. R3 does not justify hiding manual work; doing that would attract requests based on a misunderstanding.

## Revised page: version B

### See which lesson changes still need a reply

A manual confirmation tracker for independent tutors who arrange lesson changes through messages.

**Request a 15-minute prototype walkthrough**

Send a request with your preferred time. We will reply to arrange the call; this does not create an account or confirm an appointment.

### Keep outstanding changes visible

When changed lesson times sit in separate message threads, you may need to reopen each thread to check whether a reply arrived. LessonLoop gives you a list you maintain alongside those conversations.

### Add the change. Record the reply. Check what remains.

1. Add the student label and changed lesson time.
2. Update the status yourself when a reply arrives in your messaging app.
3. Open the pending list to see the changes you have not marked confirmed.

The prototype does not read messages, send reminders or update your calendar.

### See the prototype before deciding

[Placement for a verified prototype screen, captioned “Prototype view — sample data.”]

The walkthrough shows the pending list and manual updates. You can decide whether keeping this extra list fits your way of working.

**Request a 15-minute prototype walkthrough**

Want to inspect the interface first? View the example screen.

### Request form and confirmation copy

Form introduction: “Leave your email and a preferred time. We will reply to arrange a prototype walkthrough. No account is created by this request.”

Fields: email; preferred time and time zone; optional description of how you currently handle changed lessons.

Submit button: “Send walkthrough request.”

Confirmation: “Your request has been received. A time is not booked yet; look for our reply to arrange it.”

This remains draft copy. The sample screen and actual form must exist and match the copy before any publication.

## Claim ledger and revision decision

| Copy | Basis | Review |
| --- | --- | --- |
| Manual confirmation tracker | P1/P2 | Supported within the fictional specification |
| Does not read messages | P2 | Required boundary near the usage explanation |
| 15-minute walkthrough | P3 | Founder must actually offer this duration |
| Request received | Requires functioning form acknowledgement | Block publication until flow verified |
| Saves time or prevents no-shows | No basis | Excluded |

The revision moves manual work into the supporting line and explains the request beside the first button. It retains the original headline because the task was understood; it does not rewrite every element at once. No new reader check has been performed on version B, so improved comprehension is a hypothesis.

Next proposed check: show B to relevant tutors and repeat the three neutral questions. If readers understand but reject another manual list, take that finding back to positioning or product discovery. If they understand and request a walkthrough, record fit and follow-through before treating requests as meaningful demand. The three fictional observations above justify a copy revision, not a conversion claim.
