# Building a StoryBrand Worked Example

**Fictional teaching example.** All organizations, participants, numbers, and outcomes are invented for this exercise, not reported results or a case from the book.

## Visitor and problem

Visitor: an independent tutor who tracks lesson changes through messages. Desired action: request a product walkthrough. Working problem: difficulty seeing which changed times remain unconfirmed. This is a fictional positioning assumption requiring real customer research, not a quotation from a customer.

## Credibility and boundaries

The fictional prototype displays a pending list and permits manual status changes. Use a clearly labeled prototype screenshot. No customer testimonials or time-saving figures exist. Exclude “eliminates no-shows,” “trusted by hundreds,” and any claim of automated message sending.

## Steps and next action

Walkthrough flow: request a time; receive a scheduling reply; see the prototype in a short call. Primary button: Request a walkthrough. Destination: a request form asking for email and preferred time. Secondary link: View the example screen. No payment or immediate account creation is implied.

## Page draft

**Headline:** See which lesson changes still need a reply.

**Supporting line:** LessonLoop gives independent tutors one view of pending confirmations.

**Problem:** When lesson times change across separate message threads, checking who replied means opening them one at a time.

**Product:** Add a changed lesson and update its status when a reply arrives. The pending list keeps unresolved changes visible. The prototype currently requires manual updates.

**Proof:** Show a labeled prototype screen with invented names clearly marked as sample data.

**Next steps:** Request a time, receive a scheduling reply, and see the prototype in a walkthrough.

**Button:** Request a walkthrough.

## Review and measurement

“One view” and manual status updates match the fictional prototype specification. A reader might assume replies are captured automatically; the draft explicitly corrects that. Ask target readers what work remains manual and what the button does. If published later, measure qualified walkthrough requests per relevant visitor alongside misunderstandings. This is an unpublished draft; no conversion result is claimed.
